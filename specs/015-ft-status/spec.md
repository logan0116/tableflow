# Feature Specification: ft_status版本发布差距报告技能（v0.6.0）

**Feature Branch**: `015-ft-status`

**Created**: 2026-11-19

**Status**: Draft

**Input**: 需求015-AR：`ft_status` skill查看当前版本状态——逐条列出距离发布还差什么（未满足的闸门与原因），并给出拆分建议（哪些需求可移到下一个版本）；只读，不写看板；依赖008（契约口径）与010（计算落地）。

## 背景与问题证据

| 问题 | 证据 | 影响 |
|---|---|---|
| 差距说不清 | `v0.6.0`看板`发布条件`显示"否"，但不说是哪一项闸门、卡在哪一行 | 人只能逐个点开核对，容易漏 |
| 口径两套 | 看板`tf-v-cond`的options是`and(开发进度=100, 回归通过, Bug已清空, 文档状态=done)`，`board@2`的`release_gate`是`and(spec_ready, change_ready, bug_ready)` | 同一问题两个真相，报告必须点明差异 |
| 空集被读成"已回归" | `回归通过=rollup all`，本版`需求关联（依赖）`为空时结果为真 | 误以为回归做过，实际是"本版无此类工作" |
| 拆版靠拍脑袋 | 没有"哪几行可以后移、后移后还剩什么"的可复核依据 | 拆错了要么白拆、要么把依赖拆断 |
| 字段漂移 | 线上`tf-ver`缺`独立需求总数/独立需求就绪/依赖需求就绪/上一版本Bug总数`；`tf-dep`缺`证据/剩余事项/规格修订`；`fd_system`等三表项目没有`bug`表 | 按字段id硬编码的报告器在别的项目直接失效；缺缺陷表时若当0处理会给出错误的"可发布" |

口径来源：`specs/011-bug-table/board@2.yaml`（四表：`ver`/`indep`/`dep`/`bug`；`rules.release_gate`、`rules.bug_*`、`tables.*.fields`）。计算落地是010的范围；010未落地前，本技能**只读地**按契约口径在客户端重算，并在报告里标注"客户端重算"。board@2的Bug闸门以缺陷表为源：上一版本按版本号语义序取严格小于当前版本的最大版本，缺陷按`发现版本`挂接，`status != closed`计未解决。

## Clarifications

### Session 2026-11-19

- Q: "当前版本"是哪一个？ → A: 默认取"版本号大于已发布最大版本的最小`planned`版本"；显式给版本号时以参数为准；无`planned`版本则`failed`，不猜。
- Q: 闸门值从哪来？ → A: 契约口径三项就绪由本技能只读重算：`spec.acceptance`全`accepted`、`change.regress`全`passed`、上一版本未`closed`缺陷数为0（缺陷表按`发现版本`挂接）。看板同名计算字段的值同时列出，作对照，不作判据。
- Q: 空集怎么报？ → A: `change_ready`为真但标注"本版无变更单"；`spec_ready`同理。空集含义是"本版无此类工作"，不是"已验证"。
- Q: 缺字段怎么办？ → A: 按字段名解析，缺字段导致无法判定的闸门标`unknown`并说明缺哪个字段；不静默当"满足"。缺少整张`bug`表（未迁移到board@2）时，Bug闸门标"未启用"、结论写"无法完整判定"，不报错也不当0。
- Q: 悬空关联怎么处理？ → A: 版本关联里指向不存在行的id单列为"悬空关联"，按契约"悬空不得视为达标"处理，即该闸门判否。
- Q: 拆分建议是决定还是参考？ → A: 参考。技能给依赖图、候选清单与两套方案的效果对比，迁版动作由人确认，技能不写看板。
- Q: 为什么依赖010？ → A: 闸门的权威值应由010在服务端重算；010未落地前，本技能用只读重算顶替，并在报告里标"010前口径"，落地后可直接改用看板字段值。
- Q: 报告默认输出什么？ → A: 中文Markdown（人读）；`--json`输出同结构JSON（Agent读）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一屏看清能不能发 (Priority: P1)

给一个版本号，报告顶部直接回答"可发/不可发/无法完整判定"，并列出三项就绪与合成后的发布条件，每项都带判定规则与依据字段（Bug闸门的依据来自缺陷表）。

**Why this priority**: 这是唯一的结论行；结论不清楚，后面的逐条原因没人看。

**Independent Test**: 对`v0.6.0`执行，顶部出现"不可发布"、三项就绪的判定与`发布条件=否`，且每项都能指到字段名。

**Acceptance Scenarios**:

1. **Given** 一个版本号，**When** 执行报告，**Then** 顶部给出结论（可发/不可发）与三项就绪的判定，判定规则写成`board@2`的原文。
2. **Given** 三项就绪中某项为否，**When** 看结论，**Then** 报告指出卡住的行数与行id列表。
3. **Given** 三项就绪全为真，**When** 看结论，**Then** 报"可发布"，并标注空集闸门（若有）的语义。
4. **Given** 未给版本号，**When** 执行，**Then** 按"大于已发布最大版本的最小planned"选定当前版本，并在报告里写明选择依据。

---

### User Story 2 - 逐条列出还差什么 (Priority: P1)

每个未满足的闸门，逐行给出"行id / 字段现值 / 还差什么"，原因用状态机解释而不是复述字段值。

**Why this priority**: "不可发"只是结论，"哪一行、差哪一步"才是可执行信息。

**Independent Test**: `v0.6.0`的`独立需求就绪`项下逐行列出4条规格，每条给出`implement`与`acceptance`现值及补齐路径。

**Acceptance Scenarios**:

1. **Given** 某规格`implement=todo`且`acceptance=pending`，**When** 看该行原因，**Then** 写明"未开始实现；须先implement=done，再置acceptance=accepted"。
2. **Given** 某规格`implement=done`但`acceptance=pending`，**When** 看该行原因，**Then** 写明"只差验收确认"。
3. **Given** 某规格`acceptance=rejected`，**When** 看该行原因，**Then** 写明"验收被拒，需改后再验"。
4. **Given** 某变更单`regress=doing`，**When** 看该行原因，**Then** 写明"已合入待验"，并附`影响面`摘要。
5. **Given** 版本关联里存在指向已删除行的id，**When** 生成报告，**Then** 该项单列"悬空关联"，并把对应闸门判否。

---

### User Story 3 - 拆分建议可复核 (Priority: P2)

给出"哪些需求可以移到下一个版本"的建议：依赖图、候选清单、两套方案各自的效果，以及"拆版不改变闸门结论"的事实。

**Why this priority**: 版本收敛需要取舍，但取舍要能看到代价。

**Independent Test**: 对`v0.6.0`输出引用关系（谁在条款里点了谁）、未开工候选、方案A/B的保留集与移出集、下一版本号。

**Acceptance Scenarios**:

1. **Given** 同版多行规格，**When** 生成建议，**Then** 从各行`条款`文本抽取对同版其他规格编号的引用，画出依赖边。
2. **Given** 某行`implement=todo`且`acceptance=pending`，**When** 生成候选，**Then** 该行进入"可后移候选"，并给出被引用次数作为排序依据。
3. **Given** 两套方案（最小可发 / 仅移无引用者），**When** 输出建议，**Then** 分别列出保留集、移出集与移出后的剩余阻塞行数。
4. **Given** 建议生成完毕，**When** 结尾，**Then** 明确指出"迁版不改变本版闸门结论、只是缩小范围"，且说明下一版本号取自版本表而非猜测。

---

### User Story 4 - 只读保证 (Priority: P1)

整个技能只发GET，不产生任何写操作、审计与业务变更记录。

**Why this priority**: 状态报告若能顺手改数据，就没人敢在发布前跑它。

**Independent Test**: 执行前后对比`/api/tables/*/table`与行变更记录，无新增；进程内不出现`/api/agent`路径。

**Acceptance Scenarios**:

1. **Given** 任何执行，**When** 检查请求，**Then** 只调用`GET /api/projects/*`、`GET /api/tables/*`，不含`/api/agent`。
2. **Given** 执行完成，**When** 对比目标行的变更记录，**Then** 无新增记录。
3. **Given** 报告需要"下一步动作"，**When** 输出，**Then** 只给命令建议，不代为执行。

---

### User Story 5 - 口径偏差与数据异常可见 (Priority: P2)

报告把"看板计算字段与契约不一致"和"版本数据自相矛盾"单列，避免人拿旧口径当结论。

**Why this priority**: 010未落地，看板`发布条件`与契约`release_gate`不是一回事；不点明就会误判。

**Independent Test**: 对`v0.6.0`列出`发布条件`缺`spec_ready`、多`文档状态`闸门、`回归通过`带`require(状态=已完成)`、`回归状态`含`na`、缺若干契约字段，并列出`planned`早于已发布版本的行。

**Acceptance Scenarios**:

1. **Given** 看板`发布条件`的options与契约`release_gate`不同，**When** 生成报告，**Then** 列出差异项（少哪项、多哪项）并写明以契约为判据。
2. **Given** 看板`回归通过`带行级`require`，**When** 生成报告，**Then** 指出该`require`字段与契约"单字段判定"冲突。
3. **Given** 看板枚举值多出契约已删除的值（如`na`），**When** 生成报告，**Then** 列为偏差并说明判定影响。
4. **Given** 存在`planned`版本号小于已发布版本号，**When** 生成报告，**Then** 列为数据异常并给出修正建议。

### Edge Cases

- 版本关联为空：三项就绪按空集为真，但报告标注"本版无此类工作"。
- 项目只有三张表（未迁移到board@2，如`fd_system`）：缺`bug`表时Bug闸门标"未启用"、结论写"无法完整判定"，MUST NOT报错、MUST NOT把Bug数当0。
- 缺陷表存在但缺`状态`/`发现版本`字段：Bug闸门标`unknown`并说明缺哪一项。
- 上一版本没有更早版本（当前即最老版本）：Bug集合为空，按空集为真，并标注"没有更早的版本"。
- 版本行本身不存在：`failed`并列出可用版本号。
- `未清Bug数`为空（不是0）：若只有旧字段、Bug闸门仍可由缺陷表重算；缺陷表不可用时判`unknown`并说明"空值不等于0"。
- 项目字段全部漂移（找不到名字）：报告降级为"按名称兜底解析"，仍缺则标`unknown`。
- 版本号带预发布后缀或不带`v`前缀（如`7.0.2`、`v0.6.0-rc1`）：前者按语义解析，后者按字符串排序并标注无法按语义排序。

## Requirements *(mandatory)*

- **FR-001**: 技能MUST默认按"版本号大于已发布最大版本的最小`planned`版本"确定当前版本；显式版本号参数优先；无`planned` MUST `failed`。
- **FR-002**: 报告MUST逐项给出三项就绪（`spec_ready`/`change_ready`/`bug_ready`）的判定、契约规则原文与依据字段，并合成`gate`。Bug闸门MUST以缺陷表为源：按`发现版本`挂接上一版本（版本号语义序严格小于当前版本的最大版本），`status != closed`计未解决，空集为真。
- **FR-003**: 每个未满足项MUST逐行给出"行id / 字段现值 / 还差什么"，原因按状态机解释（`implement`与`acceptance`组合、`regress`取值、`bug.status`取值）。
- **FR-004**: 版本关联中的悬空id MUST单列为"悬空关联"，并使对应闸门判否。
- **FR-005**: 空集闸门MUST判真且MUST显式标注"本版无此类工作"，MUST NOT表述为"已验证"。
- **FR-006**: 技能MUST只调用GET接口，MUST NOT调用`/api/agent/*`或任何写方法。
- **FR-007**: 字段MUST按名称解析（`board@2`的名称，兼容存量叫法），MUST NOT硬编码字段id；缺字段时该闸门MUST标`unknown`并说明缺哪一项；缺整张缺陷表时MUST标"未启用"并输出"该表未迁移到board@2，Bug闸门按未启用处理"。
- **FR-008**: 报告MUST单列"看板口径偏差"：`发布条件`/`回归通过`/`回归状态`的options与契约规则、枚举、`require`的差异。
- **FR-009**: 报告MUST单列"数据异常"：`planned`版本号小于已发布版本号、版本行缺Bug字段值、缺陷表为空等。
- **FR-010**: 拆分建议MUST包含依赖边（从`条款`文本抽取同版规格编号引用）、候选清单（未开工且未accepted）、两套方案的保留/移出集、下一版本号，并声明迁版不改变本版闸门结论。
- **FR-011**: 报告MUST默认输出中文Markdown，`--json`输出同结构JSON；两者字段一致。
- **FR-012**: 技能MUST NOT建议或执行删除行、改`发布状态`、改`验收状态`等写动作；需要动作时只给命令。

## Success Criteria *(mandatory)*

- **SC-001**: 对`v0.6.0`执行，得到"不可发布"结论，`独立需求就绪=否`且逐行列出4条阻塞规格，每行带补齐路径。
- **SC-002**: 同一报告里指出看板`发布条件`与契约`release_gate`的差异至少2项（缺`spec_ready`、多`文档状态`闸门）。
- **SC-003**: 拆分建议给出依赖边与两套方案；`v0.6.0`的候选清单覆盖4条未开工规格。
- **SC-004**: 执行前后，目标行的业务变更记录条数不变；`write_audit`无新增（以只读请求清单佐证）。
- **SC-005**: 换一个字段漂移或三表的项目（如`im_kg_desktop`、`fd_system`）执行，报告仍能产出：字段漂移说明缺哪个字段，三表项目明确输出"该表未迁移到board@2，Bug闸门按未启用处理"，不崩溃、不当0。

## Non-Goals

- 不改任何看板数据（含`发布状态`、`验收状态`、版本关联）。
- 不做计算落地与重算（010的范围）。
- 不做发布动作、不打tag、不写变更说明。
- 不做工时估算、人员排期、风险打分。
- 不生成前端图表。

## Key Entities

- **当前版本（CurrentVersion）**：大于已发布最大版本的最小`planned`版本；由版本表读出。
- **闸门（Gate）**：`spec_ready`/`change_ready`/`bug_ready`/`gate`四级，规则来自`board@2.rules`；`bug_ready`的源是缺陷表，不是版本表的填报值。
- **差距行（GapRow）**：`行 id + 字段现值 + 补齐路径`三元组，逐条对应一个未满足原因。
- **漂移项（Drift）**：看板字段/枚举/计算规则与契约的差异，分"缺字段""多闸门""枚举越界""require冲突"。
- **拆分方案（SplitPlan）**：保留集、移出集、下一版本号与效果说明。
- **未迁移项目（LegacyProject）**：只有`ver`/`indep`/`dep`三张表、没有`bug`表的项目；其Bug闸门按未启用处理，报告结论降级为"无法完整判定"。
