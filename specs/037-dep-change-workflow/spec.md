# Feature Specification: 依赖需求完整变更工作流

**Feature Branch**: `037-dep-change-workflow`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 037-AR

## 背景与问题证据

| 项 | 证据 | 影响 |
|---|---|---|
| 依赖需求字段偏薄 | `dep` 表现有字段：编号、条款、关联的独立规格需求、影响面、回归状态、证据、剩余事项、规格修订、负责人 | 只有"影响面 + 回归状态 + 证据"，没有自己的计划、任务与阶段记录 |
| 跨规格变更没有编排 | 线上 `DEP-06-BR` 关联 026–031 六份规格 | 六份规格的一致性检查、集成验收没有承载位置 |
| 规格修订无产出记录 | 6 条依赖需求中 5 条 `规格修订=not_needed`、1 条为空 | 改完之后规格产生了哪一版修订无法回答 |
| 单次处理一个工作目录 | Spec Kit 一次只处理一个 feature 目录 | 关联了多份规格不代表会自动检查它们之间的一致性 |

开源对照（10 个代表项目核读，见调研记录）：`alibaba/druid` 的一次变更同时修改两个能力规格并共用设计与任务；`avoidwork/filesize.js` 的小补丁同样有完整设计与验收；`kalbasit/ncps` 的变更写明原因、影响、范围与验证；`3fn/DesignerPunk` 的补丁回链需求编号并区分验证层级。**共同点：补丁不是"改几行"，而是有完整过程的一次交付。**

## Clarifications

### Session 2026-11-23

- Q: 关联多份规格就等于一次变更吗？ → A: 不等于。仅为了连接几份规格不应产生依赖需求；必须有实际增量工作。
- Q: 小补丁能否简化流程？ → A: 可以复用既有设计与宪法，但过程证据必须对应本次工作，不能引用旧证据充数。
- Q: 规格修订字段填什么？ → A: 本次变更在目标规格上产生的修订标识；没有产生内容变化时填 `not_needed` 并说明理由。

## User Scenarios & Testing

### User Story 1 - 一次变更跨多份规格并统一编排 (Priority: P1)

某次重构同时影响两个能力的既有行为，需要统一设计、分别改条款、最后一起验收。

**Why this priority**: 当前能力缺失，跨规格变更只能靠人脑协调。

**Independent Test**: 创建一条关联两份规格的依赖需求，执行完整变更流，两份规格各自产生修订，集成验收有独立记录。

**Acceptance Scenarios**:

1. **Given** 一条依赖需求关联 026-AR 与 027-AR，**When** 记录本次增量，**Then** 能分别写出每份目标规格的基线修订与受影响条款
2. **Given** 两份规格的改动有共同设计，**When** 编排任务，**Then** 共用部分只写一次，差异部分按规格分列
3. **Given** 两份规格各自改完，**When** 执行一致性检查，**Then** 能报出两份规格之间的冲突或遗漏
4. **Given** 各规格验证通过，**When** 执行集成验收，**Then** 产出独立的集成验收记录，不与单规格验证混同

### User Story 2 - 小补丁同样走完整流程 (Priority: P1)

只改一处措辞或一个边界条件，也要留下可审计的过程。

**Why this priority**: 小改动最容易变成"直接改了没人知道"，是规格退化的主要来源。

**Independent Test**: 对一份规格做单条款修改，过程记录齐全，规模小但不缺项。

**Acceptance Scenarios**:

1. **Given** 一次只改一条验收场景的变更，**When** 记录，**Then** 仍包含增量说明、基线修订、受影响条款与验证证据
2. **Given** 本次变更复用了既有设计文档，**When** 记录复用，**Then** 写明复用哪一份、哪个版本、是否仍适用
3. **Given** 变更没有产生规格内容变化（如仅确认不受影响），**When** 收口，**Then** 规格修订填 `not_needed` 并写明判定依据

### User Story 3 - 变更产出新的规格修订 (Priority: P1)

变更完成后，规格的当前生效修订要能指向这次变更。

**Why this priority**: 与 033 的修订指针直接衔接，缺了它规格演进没有落点。

**Independent Test**: 变更完成后查询目标规格，当前生效修订的来由指向该依赖需求。

**Acceptance Scenarios**:

1. **Given** 一次变更修改了 026-AR 的规格内容，**When** 变更收口，**Then** 该规格的当前生效修订指向本次依赖需求
2. **Given** 同一规格先后被两条依赖需求修改，**When** 查询修订历史，**Then** 能按顺序列出两次修订及其基线
3. **Given** 变更涉及两份规格，**When** 收口，**Then** 两份规格各自产生一条修订，不合并成一条

### User Story 4 - 仅做关联不产生依赖需求 (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 想把三份规格标记为"相关"，但没有实际改动，**When** 尝试以此创建依赖需求，**Then** 拒绝，并提示使用规格间关联而非依赖需求
2. **Given** 一条依赖需求没有任何受影响条款，**When** 尝试推进其阶段，**Then** 拒绝

## Requirements

### Functional Requirements

- **FR-001**: 依赖需求 MUST 记录本次增量说明，写清"改什么、为什么改"
- **FR-002**: 依赖需求 MUST 为每份关联规格分别记录基线修订与受影响条款编号
- **FR-003**: 依赖需求 MUST 拥有统一的设计与任务记录，共用部分只记一次、差异部分按规格分列
- **FR-004**: 依赖需求 MUST 提供逐份规格的一致性检查，能报出跨规格的冲突与遗漏
- **FR-005**: 依赖需求 MUST 区分单规格验证与跨规格集成验收，两者各有独立证据
- **FR-006**: 变更收口时 MUST 为每份受影响的规格产出一条新修订，并在依赖需求上记录修订标识
- **FR-007**: 未产生规格内容变化的变更 MUST 允许以 `not_needed` 收口，但须写明判定依据
- **FR-008**: 依赖需求 MUST 记录所复用的既有产物的来源版本，不得以旧证据充抵本次验证
- **FR-009**: 没有实际增量（无受影响条款）的关联 MUST NOT 构成依赖需求
- **FR-010**: 依赖需求的回归状态 MUST 在集成验收通过后才可置为 `passed`

### Edge Cases

- 关联的多份规格中有一份在变更过程中被放弃（dropped），本次变更应缩范围为其余规格并重新记录影响面
- 两份规格的改动互相矛盾且无法同时满足时，一致性检查必须报冲突而不是择一通过
- 变更中途规格被其他依赖需求修改，基线不再成立，必须重新取基线而不是沿用旧基线
- 依赖需求关联了尚未验收的独立需求时，属于前提不成立，应拒绝（与 033 的 C3 一致）
- 集成验收通过但单规格验证有失败项时，回归状态不得置 passed

## Success Criteria

- **SC-001**: 任一依赖需求可在一次查询内回答"改了哪几份规格的哪些条款、基于哪个基线"
- **SC-002**: 跨规格变更的一致性检查有明确结论，冲突可被列出而非静默通过
- **SC-003**: 变更收口后，每份受影响规格的当前生效修订都能指向产生它的依赖需求
- **SC-004**: 小补丁与大变更使用同一套流程，不存在"因为小所以跳过"的路径

## Key Entities

- **依赖需求**：基于既有规格的一次增量交付，可关联多份规格
- **基线修订**：本次变更所依据的目标规格版本，改动前必须锁定
- **受影响条款**：本次变更触及的规格条款或场景编号
- **变更设计**：本次增量的统一设计记录，可跨规格共用
- **集成验收**：跨规格变更的整体验收，独立于单规格验证
- **规格修订**：变更完成后在目标规格上产生的新版本标识
