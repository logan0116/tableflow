# Feature Specification: 测试验收按版本自身执行结果判定

**Feature Branch**: `036-acceptance-own-snapshot`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 036-AR

## 背景与问题证据

只读预演已复现：对 v0.7.3 运行测试验收判定，返回通过，而该版实际有 1 条用例执行结果为 fail。

| 环节 | v0.7.3 实际状态 | 现判定口径 | 后果 |
|---|---|---|---|
| 用例是否执行 | 82 条全部 `执行状态=done` | 只看执行状态，不看执行结果 | 81 通过 1 失败被判为"全部完成" |
| 变更回归 | `DEP-06-BR` 回归状态 `passed` | 看依赖需求回归状态 | 通过 |
| 缺陷是否清空 | `BUG-06` 已在 v0.7.4 修复并置 `closed` | 读缺陷表的**全局当前状态** | 后一版本的修复被算作前一版本已清 |

两处缺陷叠加：判定漏了"结果"这一层，且回头看旧版本时读的是全局最新状态。**结果是"版本可以红灯不发布"在记录层面失效——失败过的版本事后会被算成通过。**

## Clarifications

### Session 2026-11-23

- Q: 缺陷关闭能不能作为测试通过的依据？ → A: 不能。执行结果是主判据，缺陷状态只作旁证。
- Q: 后续版本修好了，前一版本的结论要不要跟着变？ → A: 不变。原版本的验证结论是它自己的证据，不能被别的版本改写。
- Q: 一条用例失败或阻塞，版本就永远发不了吗？ → A: 不。必须给出放行通道，否则流程会被绕过。
- Q: 放行通道怎么留痕？ → A: 落在该执行行上，记录理由与批准人，不接受口头放行。

## User Scenarios & Testing

### User Story 1 - 有失败用例的版本不得通过测试验收 (Priority: P1)

测试验收要能如实反映"这一版有没有未通过的验证项"。

**Why this priority**: 这是判定失效的直接表现，也是"红灯不发布"能否成立的前提。

**Independent Test**: 对 v0.7.3 执行判定，结果必须为 failed，并列出那一条未通过的用例。

**Acceptance Scenarios**:

1. **Given** 某版本 82 条用例中 81 条结果为 pass、1 条为 fail，**When** 执行测试验收判定，**Then** 结果为 failed，并指出失败的用例号
2. **Given** 某版本全部用例结果为 pass，**When** 执行判定，**Then** 结果为 done
3. **Given** 某版本存在未执行用例，**When** 执行判定，**Then** 结果为 failed，且区分"未执行"与"执行未通过"两种原因

### User Story 2 - 后续版本的修复不改变前序版本结论 (Priority: P1)

**Why this priority**: 结论可被事后改写，等于所有历史验收记录都不可信。

**Independent Test**: v0.7.4 修复 `BUG-06` 并发布后，重新判定 v0.7.3 仍为 failed。

**Acceptance Scenarios**:

1. **Given** v0.7.3 的 `BUG-06` 在 v0.7.4 才关闭，**When** 重新判定 v0.7.3，**Then** 仍为 failed
2. **Given** 某版测试验收已记录为 failed，**When** 该版之后有版本修复了相同缺陷，**Then** 原记录不被自动改写
3. **Given** 需要对某版重新验收，**When** 在本版内补齐证据后重新判定，**Then** 允许改判，且新结论附带新的验证证据

### User Story 3 - 失败与阻塞用例的放行通道 (Priority: P1)

真实项目里存在"已知失败但本次可发"的情形，需要一条留痕的正规出口，而不是逼着人去删用例。

**Why this priority**: 没有放行通道，规则会被绕过，最终等效于没有规则。

**Independent Test**: 给一条失败用例打上放行标记，版本判定转为可发布，且报告能列出被放行的用例与理由。

**Acceptance Scenarios**:

1. **Given** 一条用例结果为 fail 且未标记放行，**When** 判定，**Then** failed
2. **Given** 一条用例结果为 fail 但已标记"不阻塞本次发布"并记录理由与批准人，**When** 判定，**Then** 通过，同时在报告中单列被放行项
3. **Given** 一条被放行的用例，**When** 查询它的放行记录，**Then** 能读到理由、批准人与时间
4. **Given** 一条用例被放行后又修复，**When** 重跑并置为 pass，**Then** 放行标记失效，不再出现在放行清单里

### User Story 4 - v0.7.3 以红灯收口 (Priority: P2)

**Acceptance Scenarios**:

1. **Given** v0.7.3 的失败项已在 v0.7.4 修复并发布，**When** 决定它的最终状态，**Then** 保留 `测试验收=failed` 不放行，或明确改为 `dropped`
2. **Given** v0.7.3 停留在 planned，**When** 查询看板版本列表，**Then** 不再出现既不推进也不结束的版本

## Requirements

### Functional Requirements

- **FR-001**: 测试验收 MUST 以本版本每条执行行的「执行结果」为主判据，全部为 pass 才可置 done
- **FR-002**: 判定 MUST 只读取本版本自己的执行行，不读取其他版本的执行结果
- **FR-003**: 缺陷状态 MUST 仅作为旁证，不得替代执行结果参与通过判定
- **FR-004**: 已记录的测试验收结论 MUST NOT 因后续版本的全局状态变化而被自动改写
- **FR-005**: 重新验收 MUST 在本版本内补齐证据后进行，并保留新旧两次结论与证据
- **FR-006**: 判定 MUST 区分"未执行"与"执行未通过"两种失败原因
- **FR-007**: 失败或阻塞的执行行 MUST 支持"不阻塞本次发布"标记，标记须记录理由、批准人与时间
- **FR-008**: 带放行标记的版本 MUST 在验收报告中单列被放行项，不得静默通过
- **FR-009**: 放行标记 MUST 落在执行行上，不得通过删除用例或缩减版本范围实现
- **FR-010**: 执行行重跑为 pass 后，其放行标记 MUST 自动失效
- **FR-011**: v0.7.3 MUST 以 `failed` 保留或以 `dropped` 终止，不得回写为通过

### Edge Cases

- 某条用例结果为 `blocked` 或 `skip` 时，按未通过处理，需要放行标记才能推进
- 一个版本没有任何执行行时，"用例是否完成"按空集为真，但测试验收不得自动通过，需明确该版无测试活动
- 同一条用例在不同版本结果不同时，各版本结论互不影响
- 缺陷表缺少该版本关联的缺陷时，按"无缺陷要清"处理，但不得据此推定执行结果通过
- 执行结果字段为空（既非 pass 也非 fail）时，按未通过处理，不得默认通过

## Success Criteria

- **SC-001**: 对 v0.7.3 的只读预演结果由"通过"变为 failed，并指出失败用例号
- **SC-002**: v0.7.4 发布后重新判定 v0.7.3，结论保持不变
- **SC-003**: 构造一次带放行标记的判定，报告能列出被放行的用例、理由与批准人
- **SC-004**: 不存在因删除用例或缩减版本范围而绕过失败项的路径

## Key Entities

- **执行行**：某条用例在某版本的一次执行，含执行状态（进度）与执行结果（结论）
- **放行标记**：附着在执行行上的"不阻塞本次发布"决定，含理由、批准人、时间
- **验收结论**：某版本测试验收的最终判定，一经记录不可被其他版本改写
- **旁证**：缺陷关闭状态等辅助信息，只用于解释，不参与判定
