# Feature Specification: 看板三表契约 board@1（v0.6.0）

**Feature Branch**: `008-board-contract`

**Created**: 2026-11-19

**Status**: Draft

**Input**: 需求 008-AR。线上7个项目21张表的字段漂移与非法写入取证后，把"表格规范写在skill文档里"改为"表格规范写在服务端契约里"。

## 背景与问题证据

| 问题 | 证据（线上155:8090，7项目21表） | 影响 |
|---|---|---|
| 字段口径漂移 | `ver`表按字段名+类型归一后有4组（17/15/18/19字段）；`indep`3组；`dep`6个项目相同、imkg多5个 | 同名不同义、同义不同名，工具与统计无法通用 |
| 类型漂移 | `回归通过`在6个项目是`computed`，在demo-im是`enum` | 同一列两种语义 |
| 命名漂移 | demo全部字段id无项目前缀（`v-ver`/`i-id`） | 无法按前缀生成与体检 |
| 状态字段被滥用 | demo-cloud的9张变更单里4条`回归状态`写成自然语言，2条为空 | 枚举形同虚设，rollup判定失真 |
| 闸门不约束写入 | v0.5.1在09:41:03写入`released`，09:41:13`发布条件`才变真 | 发布状态与发布资格脱钩 |
| 分类靠感觉 | 旧判据"是否需要独立spec"无输入、无第三类、无横切情形 | 需求落错表，事后返工 |

## Clarifications

### Session 2026-11-19

- Q: 三个比率怎么落字段？ → A: 只存`总数`与`就绪`，分子（已完成数）由展示阶段派生；判定是单字段，需要时再加一个count字段。
- Q: 依赖需求的`状态`与`回归状态`什么区别？ → A: 只保留`回归状态`作为唯一判据；`状态`删除，处置说明进`影响面`或`证据`。
- Q: 独立需求的`状态`与`验收状态`什么区别？ → A: 只保留`验收状态`；`完成 = 验收状态=accepted`；`状态`删除。
- Q: 验收状态要不要进发布条件？ → A: 不单独进；不通过即该规格未完成，经"就绪"汇总。
- Q: 是否需要额外的状态字段辅助判定？ → A: 不需要。判据唯一才不会出现两个真相；补的是三条约束（done前置、accepted后冻结、取消靠摘除关联）。
- Q: `na`要不要保留？ → A: 回归状态去掉`na`；确认不受影响也记`passed`，理由写证据。
- Q: 需求分类怎么做？ → A: 判定树（不改行为/新规格/就地改/变更单/横切），登记时必须指到规格编号与场景号。
- Q: 字段id要不要统一加前缀？ → A: 不迁移。契约用语义键做比对主键，字段id是各项目本地值。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 契约文件可被机器读取 (Priority: P1)

任何人或Agent打开`specs/008-board-contract/board@1.yaml`，能读到三张表的每个字段：语义键、名称、类型、枚举、必填、是否闸门，以及状态定义、完成判定、分类判定树。

**Why this priority**: 这是后续009/010/011/015取口径的唯一来源；没有它，每条需求都会各自定义字段。

**Independent Test**: 用YAML解析器读取文件，字段数与三表规模一致（16/16/9），`tables.*.fields[*].key`无重复。

**Acceptance Scenarios**:

1. **Given** 契约文件，**When** 解析，**Then** 得到`ver`16字段、`indep`16字段、`dep`9字段，且每个字段都有`key`/`name`/`type`。
2. **Given** 契约中标记`gate: true`的字段，**When** 统计，**Then** 恰好4个（`spec_ready`/`change_ready`/`bug_ready`/`gate`）。
3. **Given** 契约的`status_definitions`，**When** 逐项核对，**Then** 每个状态只回答一个问题，且`values`集合互不重叠语义。

### User Story 2 - 契约与看板现状可对照 (Priority: P1)

拿契约对照任意项目，能说清差异在哪（缺字段、类型不符、字段id不合规、语义未登记），且不改动任何行数据。

**Why this priority**: 不先可对照，就无法判断"落地了没有"，也挡住了存量迁移的粗暴做法。

**Independent Test**: 对demo逐字段比对，能报出"字段id无项目前缀"与"缺`已勾选任务数`"，且全程只读。

**Acceptance Scenarios**:

1. **Given** tableflow项目，**When** 按语义键比对，**Then** 能指出`开发进度`/`测试进度`/`未清Bug数`等7个字段不在契约内。
2. **Given** demo-im的`回归通过`是`enum`，**When** 比对契约声明的`computed`，**Then** 报告类型不符。
3. **Given** 比对过程，**When** 检查写入审计，**Then** 无任何写操作。

### User Story 3 - 分类判据可复核 (Priority: P2)

给一条需求，能按判定树走到唯一一张表，并留下可核验依据（规格编号+场景号）。

**Why this priority**: 分类错了，后面的登记、挂版本、回归全都白做。

**Independent Test**: 取三条真实需求（新增能力/改已完成规格/改未完成规格），各自走出唯一结论且依据能指到spec.md里的场景。

**Acceptance Scenarios**:

1. **Given** 需求改变已`accepted`规格的行为，**When** 走判定树，**Then** 结论为`dep`变更单，且必须挂该规格。
2. **Given** 需求是现有规格未覆盖的新能力，**When** 走判定树，**Then** 结论为`indep`新行。
3. **Given** 需求不改变产品行为（部署/环境），**When** 走判定树，**Then** 结论为不进看板。
4. **Given** 判据指不到任何规格与场景，**When** 尝试登记，**Then** 判定树要求先追问，不允许落行。

### Edge Cases

- 一条需求同时新增能力又改动已完成规格：拆成一条`indep`与一条`dep`，影响面互相引用。
- 一次改动横切多份已完成规格：一张`dep`挂多份规格，影响面分别写清。
- 规格取消：从版本关联摘除或删行，不用验收状态表达"不做"。

## Requirements *(mandatory)*

- **FR-001**: 契约以YAML文件交付，位于`specs/008-board-contract/board@1.yaml`。
- **FR-002**: `ver`表16字段，含`独立需求总数/就绪`、`依赖需求总数/就绪`、`上一版本Bug总数/未解决数/就绪`、`发布条件`。
- **FR-003**: `indep`表16字段，`验收状态`为唯一完成判据，`implement`为进度记录与前置条件。
- **FR-004**: `dep`表9字段，`回归状态`为唯一完成判据；`证据`/`剩余事项`/`规格修订`为记录字段。
- **FR-005**: 契约声明四个状态域（阶段/验收/回归/发布），每个状态只回答一个问题。
- **FR-006**: 契约声明判定规则：`spec_done=accepted`、`change_done=passed`、空集为真、发布条件=三项就绪。
- **FR-007**: 契约声明分类判定树（5个分支）与"必须指到规格编号与场景号"的依据要求。
- **FR-008**: 契约显式列出非目标：计算落地、接口改造、写入校验、存量迁移、展示。
- **FR-009**: 契约用语义键做比对主键，不要求存量项目改字段id。
- **FR-010**: 契约文件与看板skill的表述一致；skill中"没有第四张表"的表述在011落地时同步修改。

## Success Criteria *(mandatory)*

- **SC-001**: YAML可解析，三表字段数16/16/9，`key`无重复。
- **SC-002**: 拿契约能对任一项目产出差异清单，且清单里的每条差异能指到具体字段与原因。
- **SC-003**: 判定树对三条真实需求给出唯一结论，依据可指到spec.md场景。
- **SC-004**: 契约正文中不含任何接口、代码、迁移步骤。

## Non-Goals

- 计算口径落地与重算（010）。
- bug表与第四张表（011）。
- 接口协议（012）、用户管理（013）。
- 存量字段改名、项目迁移。
- 前端展示。

## Key Entities

- **ver（版本管理）**：一个发布版本；聚合三项就绪。
- **indep（独立规格需求）**：一份规格；`验收状态`判完成。
- **dep（依赖需求）**：一张变更单；`回归状态`判完成。
- **语义键**：形如`ver.spec_ready`，契约内唯一，跨项目稳定。
- **闸门字段**：参与发布条件的计算字段，禁止人工覆盖。
