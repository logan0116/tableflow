# Feature Specification: 版本表界面合并显示

**Feature Branch**: `026-ver-columns`

**Created**: 2026-11-22

**Status**: Draft

**Input**: 需求 026-AR。board@4 落地后版本表 26 列，横向滚动才能看到发布条件与关联清单；六节点、三组关联（独立需求/依赖需求/测试用例/Bug）各自拆成「关联 + 比率 + 是否完成」三列，同一件事占了三个位置。本需求只改界面渲染：把分散的列合并成可读的组，字段与判定口径一律不动。

## 背景与问题证据

| 问题 | 证据 | 影响 |
|---|---|---|
| 版本表过宽 | board@4 的 `ver` 有 26 字段，1280 宽下要横向滚动数屏才看到发布条件 | 判断"这版能不能发"要先滚很久 |
| 同一事实占三列 | 独立需求 = `独立需求管理` + `独立需求已完成/总数` + `独立需求是否完成`，依赖需求/测试/Bug 同构 | 三列说的是同一件事，扫读成本高 |
| 节点状态分散 | 六个四态节点 + `六节点是否全部完成` 共 7 列 | 看不出"卡在第几个节点" |

## Clarifications

### Session 2026-11-22

- Q: 改不改契约与接口？ → A: 不改。字段、计算口径、写接口、门禁全部保持 board@4 原样；本需求只改前端渲染。
- Q: 合并后还能看到原始状态吗？ → A: 能。灯的颜色与悬停文案给出节点名与四态；关联列点击弹窗展示清单，弹层第三列仍是完成判据字段。
- Q: 发布条件放在哪？ → A: 保留独立一列，与灯组并列显示；灯组全绿时该列为「是」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 六节点合并为灯组 (Priority: P1)

版本行的六个节点与汇总字段合并为一组状态灯，一眼看出卡在第几个节点、是否全绿。

**Why this priority**: 判断"这版走到哪"是版本表最常被问的问题。

**Independent Test**: 打开版本表，数节点列；v0.7.0 行应显示 6 个绿灯且发布条件为「是」。

**Acceptance Scenarios**:

1. **Given** 版本表渲染完成，**When** 数表头，**Then** 六个节点与「六节点是否全部完成」不再各占一列，而是一组 6 个灯加一个汇总指示。
2. **Given** 某版本六节点全为 `done`（如 v0.7.0），**When** 看该行，**Then** 6 个灯全绿，发布条件显示「是」。
3. **Given** 某版本六节点有 `todo/doing/failed`，**When** 看该行，**Then** 对应灯显示非绿状态，且能分辨是哪一个节点。
4. **Given** 鼠标悬停某个灯，**When** 停留，**Then** 提示里含节点名与该节点的四态文案。

### User Story 2 - 独立需求三列合并为一列 (Priority: P1)

「独立需求管理」「独立需求已完成/总数」「独立需求是否完成」合并为一列，显示已完成/总数，点击弹窗看清单。

**Why this priority**: 三列同源，合并后腾出的宽度让其他组也能展示。

**Independent Test**: v0.7.0 行该列显示 `7/7`，点击弹出 7 条需求清单。

**Acceptance Scenarios**:

1. **Given** 版本表渲染完成，**When** 看表头，**Then** 独立需求只剩一列，不再有「独立需求管理/已完成总数/是否完成」三列。
2. **Given** 某版本关联了 7 份规格且全部 accepted，**When** 看该列，**Then** 显示 `7/7`。
3. **Given** 某版本未关联任何规格，**When** 看该列，**Then** 显示 `0/0` 且仍可点击。
4. **Given** 点击该列，**When** 弹窗打开，**Then** 列出该版本关联的全部需求行（编号 + 条款摘要 + 验收状态）。

### User Story 3 - 依赖需求、测试、Bug 同构合并 (Priority: P1)

其余三组按与独立需求完全相同的规则合并。

**Why this priority**: 四组结构一致，不一致的呈现会让扫读重新变累。

**Independent Test**: 四组列头形状一致，点击都弹清单。

**Acceptance Scenarios**:

1. **Given** 版本表渲染完成，**When** 看表头，**Then** 依赖需求、测试（用例）、Bug 三组各自只剩一列。
2. **Given** 某版本依赖需求 2 条全通过，**When** 看该列，**Then** 显示 `2/2`。
3. **Given** 某版本纳入 150 条用例且全部执行，**When** 看测试列，**Then** 显示 `150/150`。
4. **Given** 点击任一组列，**When** 弹窗打开，**Then** 列出该组关联行，第三列显示该组的完成判据（验收状态/回归状态/执行状态/缺陷状态）。

### User Story 4 - 只改渲染，判定不变 (Priority: P1)

合并后发布条件、比率、是否完成的判定与 board@4 完全一致，接口与契约不变。

**Why this priority**: 这是界面改动，不能顺手改掉判定口径。

**Independent Test**: 合并前后同一版本的发布条件读回值一致；`check_board` 差异 0。

**Acceptance Scenarios**:

1. **Given** 合并后的界面，**When** 对比接口返回的 `发布条件` 与界面显示，**Then** 两者一致。
2. **Given** 合并前后同一份数据，**When** 跑 `check_board --base`，**Then** 差异仍为 0。
3. **Given** 合并后的界面，**When** 用 `tf-status` 只读查询版本差距，**Then** 输出与合并前一致。

## Requirements *(mandatory)*

- **FR-001**: 版本表 MUST 把六个节点与「六节点是否全部完成」渲染为一组灯，MUST NOT 各占独立列。
- **FR-002**: 灯组 MUST 能区分六个节点各自的状态（todo/doing/done/failed），MUST 提供节点名与状态文案（悬停或等价方式）。
- **FR-003**: 独立需求、依赖需求、测试（用例）、Bug 四组 MUST 各自合并为一列，显示「已完成/总数」。
- **FR-004**: 四组合并列 MUST 可点击，弹窗 MUST 复用现有关系弹层（006 的列头推导），MUST NOT 新造弹窗组件。
- **FR-005**: 合并 MUST 只影响渲染；字段、计算字段、写接口、门禁校验 MUST 保持 board@4 原样。
- **FR-006**: 空集 MUST 显示 `0/0` 且仍可点击（与 empty_set 语义一致）。
- **FR-007**: 发布条件、发布状态、负责人、变更说明 MUST 保留独立列。

## Non-Goals

- 不改契约、不加字段、不改计算口径。
- 不改后端接口与写校验。
- 不改角色切换与配色（022 的范围）。
- 不做列的自定义显示配置（那是 006 的范围，本需求只做固定合并）。

## Success Criteria

- 版本表在 1280 宽下不需要横向滚动就能看到灯组与四组合并列。
- v0.7.0 行：6 灯全绿、独立需求 `7/7`、测试 `150/150`、发布条件「是」。
- 合并前后 `check_board` 差异为 0，`tf-status` 输出一致。
