# Feature Specification: 未完成需求的范围拆分与放弃

**Feature Branch**: `034-scope-split-drop`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 034-AR

## 背景与问题证据

| 项 | 证据 | 影响 |
|---|---|---|
| 未完成需求没有切分路径 | `board@4.yaml` 的 `classify.order` 只有 `in_place`（未 accepted 时直接改 spec 与 indep 行）、`change`（已 accepted 后开 dep）、`new_spec`、`cross`、`out_of_board` | 一条做不完的需求只有"继续做"一条路，想把剩余部分切出去没有合法动作 |
| 取消语义只表达"不做" | `rules.spec_cancel`：取消的规格从版本关联摘除或删行 | 摘除或删行都不保留"当时做到哪、为什么停"，事后无法审计 |
| 缺少终止态 | 独立需求的 `验收状态` 只有 pending / accepted / rejected | 一条确定不做的需求只能长期停在 pending，或被迫写成 accepted |

本需求补两个动作：**拆分**（把剩余范围切给新需求，原需求继续）与**放弃**（整条终止，保留当时结论）。放弃是唯一新增的**终态**；拆分不是终态，是一种范围调整动作。

## Clarifications

### Session 2026-11-23

- Q: 拆分是不是终态？ → A: 不是。拆分是动作：原需求保留一部分继续交付，另一部分由新建的关联需求承接，原需求继续存在。
- Q: 放弃后原记录怎么写？ → A: 保留当时未完成的结论，注明放弃理由与时间；不得回写为验收通过。
- Q: 已放弃需求对应的规格能否再被依赖需求修改？ → A: 不能。依赖需求的前提是目标规格已验收通过；能力未建立时没有可修改的对象。要重新建立该能力，走新的独立需求。
- Q: 已 accepted 的需求能否拆分？ → A: 不能。已 accepted 之后的范围变化走依赖需求。

## User Scenarios & Testing

### User Story 1 - 拆分一条做不完的需求 (Priority: P1)

系统工程发现某条需求工作量超出本版，需要把其中一部分留在本版继续做，另一部分交给新需求另排期。

**Why this priority**: 这是"没完成就拆依赖需求"这条口径唯一缺失的动作。

**Independent Test**: 对一条 pending 的需求执行拆分，原需求的范围缩小、新需求出现并反向指回原需求，两条都能被独立查询。

**Acceptance Scenarios**:

1. **Given** 035-AR 处于 pending 且挂在本版，**When** 把其中 US3 与 US4 拆分出去，**Then** 原需求范围缩减为 US1 与 US2，仍挂在本版，验收状态保持 pending
2. **Given** 一次拆分完成，**When** 查询承接方，**Then** 新建需求携带被移交的 US3 与 US4，并在记录中指回 035-AR
3. **Given** 一次拆分完成，**When** 查询原需求，**Then** 记录中包含拆分时间、移交的条款编号、承接方编号
4. **Given** 原需求后来完成，**When** 它被判为 accepted，**Then** 验收只覆盖保留下来的 US1 与 US2

### User Story 2 - 放弃一条不做的需求 (Priority: P1)

需求最终确认不做，需要留痕终止，而不是长期挂在版本上。

**Why this priority**: 没有终止态，看板会积累永不结束的行，发布闸门也无法判定。

**Independent Test**: 对一条 pending 需求执行放弃，其验收状态变为 dropped 且不再出现在任何版本的交付范围里。

**Acceptance Scenarios**:

1. **Given** 一条 pending 需求已挂在本版，**When** 执行放弃并填写理由，**Then** 验收状态变为 dropped，版本关联被摘除
2. **Given** 一条需求被放弃，**When** 查询它的历史，**Then** 仍能看到放弃前的阶段状态与未完成的结论
3. **Given** 一条需求被放弃，**When** 尝试把它的验收状态改为 accepted，**Then** 拒绝修改，终态不可回退

### User Story 3 - 拆分与放弃之后仍然可追溯 (Priority: P2)

半年后回看，要能回答"这条需求为什么缩小了、剩下的去哪了、为什么不做了"。

**Why this priority**: 追溯缺失会让拆分退化成"删掉不想要的部分"。

**Independent Test**: 给定任一被拆分或被放弃的需求，能在一次查询内得到完整的变更链。

**Acceptance Scenarios**:

1. **Given** 一条被拆分的需求，**When** 追溯，**Then** 能得到"原范围 → 移交条款 → 承接需求 → 承接需求的结局"完整链
2. **Given** 一条被放弃的需求，**When** 追溯，**Then** 能得到放弃理由、放弃时间与放弃时的阶段快照
3. **Given** 承接需求后来又被拆分，**When** 追溯，**Then** 链条可继续向下展开，不丢中间节点

### User Story 4 - 非法操作被明确拒绝 (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 一条已 accepted 的需求，**When** 尝试拆分，**Then** 拒绝并提示应走依赖需求
2. **Given** 一条已 dropped 的需求，**When** 尝试重新挂到某个版本，**Then** 拒绝并提示应新建独立需求
3. **Given** 一条已 dropped 需求的规格，**When** 尝试新建依赖需求修改它，**Then** 拒绝并说明前提不成立
4. **Given** 一个已发布版本里的需求，**When** 尝试拆分或放弃它，**Then** 拒绝，历史结论不得改写

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 提供「拆分」动作：把未完成需求的部分条款/场景移交给一条新建的关联需求
- **FR-002**: 拆分 MUST 仅在原需求验收状态为非 accepted 时允许
- **FR-003**: 拆分后原需求 MUST 继续存在，并继续承接未被移交的部分
- **FR-004**: 拆分 MUST 在原需求上留痕：拆分时间、移交的条款或场景编号、承接方编号
- **FR-005**: 承接方 MUST 反向指回原需求，形成可双向追溯的关联
- **FR-006**: 被移交的条款 MUST 从原需求移出（引用式移交），不得在两处同时生效
- **FR-007**: 系统 MUST 把「放弃」定义为独立需求的唯一新增终态，取值为 `dropped`
- **FR-008**: 放弃 MUST 保留当时的阶段状态快照与未完成结论，并记录理由与时间
- **FR-009**: 放弃 MUST 摘除该需求与所有版本的关联，且不得回写为 accepted
- **FR-010**: 已 dropped 需求的规格 MUST 拒绝新增依赖需求；该能力如需重建，MUST 走新的独立需求
- **FR-011**: 拆分与放弃 MUST 拒绝作用于已发布版本中的需求，不得改写历史结论
- **FR-012**: 拆分与放弃 MUST 原子执行，失败时原需求与原版本关联保持操作前状态

### Edge Cases

- 拆分时只移交部分场景而非整个 User Story，移交粒度以场景号为准，避免整故事搬迁
- 原需求的全部条款都被移交时，应视为"整体转让"而不是留一条空壳需求；此时要求先放弃原需求再新建
- 承接方本身又被拆分时，链条允许嵌套，追溯需能展开多层
- 已 dropped 需求若已在某版本产生过用例执行记录，这些记录保留，不随需求放弃而删除
- 拆分与放弃的目标需求正被其他会话修改时，操作应失败并给出可重试提示，不得基于过期快照写入

## Success Criteria

- **SC-001**: 一条做不完的需求可在不新建独立需求的前提下，把剩余范围切给新需求，且原需求记录完整保留
- **SC-002**: 放弃后的需求不再出现在任何版本的交付范围统计中，且其历史阶段状态仍可查询
- **SC-003**: 任一被拆分或被放弃的需求，可在一次查询内得到完整变更链，无需人工拼接
- **SC-004**: 已发布版本的需求无法被拆分或放弃，历史结论零改写

## Key Entities

- **拆分记录**：描述一次范围切割，含原需求、承接需求、移交条款清单、时间与操作者
- **承接需求**：因拆分而新建的关联需求，承担被移交的部分
- **放弃记录**：终止一条需求，含理由、时间与放弃时的阶段快照
- **终态**：`accepted`（完成）与 `dropped`（放弃）两种，其余状态均为过程态
