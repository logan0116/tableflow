# Feature Specification: 交付记录与规格演进分离

**Feature Branch**: `033-delivery-vs-spec`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 033-AR

## 背景与问题证据

| 项 | 证据 | 影响 |
|---|---|---|
| 独立需求跨版本重复 | 线上 v0.7.1 / v0.7.3 / v0.7.4 都挂了 026–028，v0.7.2 / v0.7.3 / v0.7.4 都挂了 029–031；另有 007-AR 同时挂 v0.5.0 与 v0.5.1 | 7 条需求、13 处重复；同一交付工作被重复计入多个版本 |
| 规格演进无记录载体 | `DEP-06-BR` 的「规格修订」字段为空，其余 5 条为 `not_needed` | 无法回答"这份规格现在生效的是哪一版、由谁产生" |
| 三者混用 | 「独立需求」被当成「规格」的别名 | "完成即冻结"与"规格可演进"两种理解同时存在，规则无法统一 |

本需求把三个对象分开：**规格是能力约定，可长期修订；独立需求是首次建立该能力的一次交付；依赖需求是其后的一次增量。** 冻结的是交付记录，不是规格内容。

## Clarifications

### Session 2026-11-23

- Q: 规格与独立需求是什么关系？ → A: 规格是能力的行为约定，长期存在并可修订；独立需求是首次建立该能力的**一次交付工作**，完成后不再重新打开。
- Q: 依赖需求能否在多个版本出现？ → A: 不能。一次增量只属于一个版本。
- Q: 依赖需求能否与其关联的独立需求同一版本？ → A: 可以。禁止的是**早于**，同版本合法。
- Q: 规格内容改了以后，原来的独立需求要不要重新验收？ → A: 不要。原独立需求保留当时的交付结论；新修订由产生它的依赖需求自带验收。

## User Scenarios & Testing

### User Story 1 - 区分规格、独立需求、依赖需求 (Priority: P1)

系统工程需要能回答：这个能力是谁建立的、后来被谁改过、现在生效的是哪一版行为约定。

**Why this priority**: 三者混用是所有下游问题的根因，也是本条其余三个故事的前提。

**Independent Test**: 对 026 能力查询，应返回首次建立它的独立需求 026-AR、历次依赖需求，并能指出当前生效修订由哪条依赖需求产生。

**Acceptance Scenarios**:

1. **Given** 规格目录 `specs/026-ver-columns/`，**When** 查询它的交付记录，**Then** 返回首次建立该能力的独立需求 026-AR 与历次依赖需求列表
2. **Given** 027-AR 已验收通过，**When** 通过依赖需求修改该规格的验收条款，**Then** 027-AR 行不被重新打开，规格内容产生一条新修订
3. **Given** 一份规格没有任何后续依赖需求，**When** 查询当前生效修订，**Then** 返回"首次修订"，来源指向它的独立需求

### User Story 2 - 唯一性与先后约束 (Priority: P1)

同一次交付工作不能在多个版本重复计入，依赖需求不能出现在它所依据的能力建立之前。

**Why this priority**: 唯一性是"完成就是完成"在数据层的唯一可校验形式。

**Independent Test**: 对已挂在 v0.7.1 的 026-AR 再执行一次挂载到 v0.8.0，应被拒绝并返回冲突版本。

**Acceptance Scenarios**:

1. **Given** 026-AR 已挂在 v0.7.1，**When** 尝试把它挂到 v0.8.0，**Then** 拒绝，并返回规则号 C1 与已占用的版本号
2. **Given** DEP-06-BR 已挂在 v0.7.3，**When** 尝试把它挂到另一个版本，**Then** 拒绝，并返回规则号 C2
3. **Given** DEP-06-BR 关联 026-AR（v0.7.1），**When** 把它挂到 v0.7.0，**Then** 拒绝，并说明早于其关联独立需求所在版本
4. **Given** DEP-01-BR 与 003-AR 同属 v0.3.0，**When** 校验先后关系，**Then** 通过（允许同版本）
5. **Given** 一条依赖需求关联多份规格且分属不同版本，**When** 挂到早于其中最晚者的版本，**Then** 拒绝

### User Story 3 - 历史数据按规则清理 (Priority: P2)

新规则生效后，把已存在的重复挂载清成唯一归属，且不改变各版本已有的测试结论。

**Why this priority**: 规则只对新数据生效会让看板长期保留 13 处违反，无法作为判据。

**Independent Test**: 清理后遍历所有版本的「独立需求管理」并集，每个编号计次均为 1。

**Acceptance Scenarios**:

1. **Given** 007-AR 同时挂在 v0.5.0 与 v0.5.1，**When** 执行清理，**Then** 只保留 v0.5.0，v0.5.1 摘除
2. **Given** 026–028 各挂三个版本，**When** 执行清理，**Then** 只保留 v0.7.1
3. **Given** 029–031 各挂三个版本，**When** 执行清理，**Then** 只保留 v0.7.2
4. **Given** v0.7.3 与 v0.7.4 被摘除需求关联，**When** 回读这两版的用例关联与依赖需求关联，**Then** 均保持不变
5. **Given** 清理完成，**When** 复算 v0.7.3 的测试验收，**Then** 仍为 failed（不因摘除需求而转绿）

### User Story 4 - 拒绝时给出可操作信息 (Priority: P2)

被拒绝的人要能立刻知道冲突在哪、该改哪一行。

**Why this priority**: 只报"不允许"会让流程卡住，实际使用时会被绕过。

**Independent Test**: 制造一次 C1 冲突，检查返回体是否含规则号、冲突行 id、已占用版本。

**Acceptance Scenarios**:

1. **Given** 一次违反 C1 的挂载请求，**When** 被拒绝，**Then** 返回体包含规则号、冲突行 id、已占用版本号与修复建议
2. **Given** 一次挂载操作中途失败，**When** 回读目标版本行，**Then** 该行关联保持操作前状态，不出现部分写入

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 把规格、独立需求、依赖需求定义为三种不同对象，各自有独立标识与生命周期
- **FR-002**: 系统 MUST 保证同一独立需求在所有版本的「独立需求管理」中出现次数不超过 1（规则 C1）
- **FR-003**: 系统 MUST 保证同一依赖需求在所有版本的「依赖需求管理」中出现次数不超过 1（规则 C2）
- **FR-004**: 系统 MUST 拒绝把依赖需求挂到早于其关联独立需求的版本，允许同版本（规则 C3）
- **FR-005**: 当依赖需求关联多份规格时，系统 MUST 以其中**最晚**交付的独立需求所在版本作为 C3 的比较基准
- **FR-006**: 系统 MUST 能给出某份规格的当前生效修订，以及产生该修订的依赖需求编号；无后续依赖需求时指向其独立需求
- **FR-007**: 违反 C1/C2/C3 时，系统 MUST 返回规则号、冲突行 id、已占用版本与修复建议
- **FR-008**: 挂载操作 MUST 原子执行，失败时目标版本行的关联保持操作前状态
- **FR-009**: 引擎 MUST 在任何写入路径上校验 C1/C2/C3；技能 MUST 使用与引擎同源的规则，不得各写一份
- **FR-010**: 系统 MUST 对历史清理留存前后对比记录（被摘除的行 id 与来源版本）
- **FR-011**: 历史清理 MUST 保留被摘除的原始挂载证据（写入版本备注或审计日志），不得无痕删除
- **FR-012**: 历史清理 MUST 在需求 036（测试验收按版本自身执行结果判定）生效之后执行

### Edge Cases

- 规格目录被重命名后，历史交付记录仍需能按需求编号追溯，不依赖目录名
- 依赖需求关联的多份规格分属不同版本时，C3 取最晚者；若其中一份尚未交付（无版本），该依赖需求不得挂载
- 独立需求被放弃（dropped）后，其规格是否允许被依赖需求继续修改，需在契约中给出明确取值，不能留空
- 依赖需求关联的独立需求行被删除时，校验应报"关联目标不存在"而不是静默通过
- 版本号形态不一致（`7.0.0` 与 `v7.0.0`）时，语义排序必须归一化后再比较
- 清理执行期间有其他会话正在修改同一版本行时，清理应失败并给出可重试提示，不得基于过期快照写入

## Success Criteria

- **SC-001**: 线上跨版本重复挂载从当前 13 处降为 0
- **SC-002**: 构造的 C1/C2/C3 违反用例 100% 被拒绝，且返回体含规则号
- **SC-003**: 任一规格可在一次查询内回答"当前生效修订"与"产生它的依赖需求"，无需人工拼接
- **SC-004**: 历史清理前后，v0.7.3 的测试验收结论保持 failed，v0.7.4 保持 released 且发布条件为真
- **SC-005**: 清理记录可复现：给定记录可还原清理前的挂载状态

## Key Entities

- **规格（spec）**：某项能力的行为约定，位于 `specs/<dir>/`，可持续修订；本身不是交付工作
- **独立需求**：首次建立某项能力的一次交付工作，编号 `NNN-AR`，终态为 `accepted` 或 `dropped`
- **依赖需求**：基于既有规格的一次增量（补充/修改/补齐/跨规格集成），编号 `DEP-NN-BR`，关联一份或多份规格
- **版本**：一次发布，持有本次的交付记录（独立需求与依赖需求）与测试结论；不含规格内容本身
