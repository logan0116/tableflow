## 三、被推翻的结论

### 3.1 “121 条场景全部通过”

| 事实 | 数据 |
|---|---|
| 场景数 | 121 |
| 每条映射的测试数 | 全部为 1 |
| 不同测试函数数 | 83 |
| 与他场景共用同一测试的场景 | 38 |
| 已确证语义不对应 | 2（`038-US1-AS2`、`040-US2-AS3`） |
| 自检强度 | 只验证被引用函数在文件里存在 |

345→349 全绿只证明“引擎按现有测试的行为正确”，不证明“121 条场景被逐条验证”。该结论需要逐条复核后重出，不能作为发布依据。

### 3.2 “75% 规格没有规范内容，导致 plan/tasks 被跳过”

对 specs 001-032 共 31 份规格实测：

| 口径 | 有 FR 的规格 | FR 中位数 |
|---|---|---|
| 分析器 `analyze()` | 8/31 | 0 |
| 文本中实际存在的 `- **FR-###**` | 30/31 | 12 |

抽查：026 = 7 条、027 = 5 条、028 = 6 条，分析器全部报 0。

根因：`spec_structure.py:109` 只在 `section == "functional_requirements"` 时计数，而 `SECTION_KEYS` 把 `## Requirements` 映射为 `requirements`。这些规格把 FR 直接写在 `## Requirements *(mandatory)*` 下（026/028 均如此），因此整段被忽略；只有另开 `### Functional Requirements` 子章节的 8 份被计入。

结论：**“规格没有内容”没有任何证据支撑**，039 的差距报告与“plan/tasks 被跳过”的归因需要撤回重算。分析器本身是缺陷（P2），不是规格的缺陷。

## 四、共同根因

1. **契约写通用口径，实现写死形状或类型。** 版本号被当成 `vX.Y.Z`（run id、技能正则、连 020 的 FR-001 文本都这么写），用例表因为有“指向验收表的关系”被当成依赖需求表。同一个错误在服务端、技能、契约三处各写了一遍。
2. **表类型靠启发式识别。** 判据是“有没有验收枚举 / 有没有六节点 / 有没有回归枚举”，没有显式 kind。`run_protocol.py` 的注释自己写明「kind 落库属 019 实现范围」——没有 kind 就只能猜，猜错就误伤，新增一张带相似枚举的表还会再错一次。
3. **写入模式与原子性没有统一入口。** `dry_run` 在每条写路径上各自判断（所以出现 `--apply --dry-run` 真写）；“摘版本关系 + 改需求状态”这种跨行写没有事务边界，只能靠客户端逐条补偿。
