# Feature Specification: 看板规则固化

**Feature Branch**: `040-rule-enforcement`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 040-AR

## 背景与问题证据

| 项 | 现状 | 影响 |
|---|---|---|
| 契约只能表达字段级约束 | `board@4.yaml` 有字段类型、枚举取值、计算字段与 relation 定义 | 跨行唯一性、版本先后、原子性这类规则无处可写 |
| 引擎没有跨行校验 | 后端对 relation 写入只校验字段合法性，不校验"该行是否已属别的版本" | 违规写入畅通无阻 |
| 技能各写一份校验 | 各技能在自己的脚本里判断，同一规则可能有多套实现 | 规则漂移，改一处漏一处 |
| 规则散落在文档与代码注释 | 如"完成就是完成""不可回退"等口径只存在于技能说明与讨论记录 | 无法枚举、无法回归、新人无法核对 |

本需求把**契约表达不了的规则**统一固化到三个位置：**引擎**（写入期拦截）、**技能**（执行前自检）、**文档**（可枚举的规则清单），并保证三者同源。

## Clarifications

### Session 2026-11-23

- Q: 哪些规则需要固化？ → A: 契约 YAML 无法表达的全部规则，典型如 033 的 C1/C2/C3 唯一性与先后约束、034 的拆分与放弃前置条件、036 的结论不可改写。
- Q: 引擎与技能各写一份可以吗？ → A: 不可以。必须同源，技能侧读取同一份规则定义或直接调用引擎校验，避免两套实现漂移。
- Q: 文档要写到什么程度？ → A: 每条规则有编号、含义、判定式、实现位置与反例，足以让人照着写测试。

## User Scenarios & Testing

### User Story 1 - 引擎在写入期拦住违规操作 (Priority: P1)

任何路径写入看板，违反规则都必须失败，而不是靠调用方自觉。

**Why this priority**: 只在技能层校验，绕过技能手工写就拦不住；而手工绕过正是当前重复挂载的成因之一。

**Independent Test**: 直接调用写入接口制造一次 C1 冲突，应返回错误且不落库。

**Acceptance Scenarios**:

1. **Given** 026-AR 已属 v0.7.1，**When** 直接调用接口把它加入 v0.8.0 的独立需求管理，**Then** 返回 4xx 且不写入
2. **Given** 一次写入违反 C3，**When** 提交，**Then** 返回错误并指明违反的规则号
3. **Given** 一次合法的挂载，**When** 提交，**Then** 正常写入，且不因校验产生额外延迟

### User Story 2 - 技能使用同源规则自检 (Priority: P1)

技能在动手之前先自查，给出比引擎错误更可读的说明。

**Why this priority**: 引擎只负责拦住，技能负责解释；两套规则不同步则会互相矛盾。

**Independent Test**: 技能侧的校验结论与引擎侧对同一输入应完全一致。

**Acceptance Scenarios**:

1. **Given** 一次违反 C1 的挂载，**When** 技能自检，**Then** 在发请求前就失败，并给出冲突行与已占用版本
2. **Given** 规则定义更新，**When** 技能下次执行，**Then** 使用新规则，无需改技能代码
3. **Given** 构造一组规则用例，**When** 分别跑引擎与技能，**Then** 两侧判定结果逐条一致

### User Story 3 - 规则可枚举、可回归 (Priority: P1)

**Why this priority**: 不可枚举的规则无法被检验，也无法在改动时确认没破坏。

**Independent Test**: 给出规则清单即可生成测试集，覆盖每条规则的正例与反例。

**Acceptance Scenarios**:

1. **Given** 规则清单，**When** 查看任一条，**Then** 能看到编号、含义、判定式、实现位置与反例
2. **Given** 新增一条规则，**When** 提交，**Then** 必须同时提交文档条目与至少一个反例测试，否则不算完成
3. **Given** 一次契约改动涉及既有规则，**When** 合并，**Then** 相关规则条目同步更新并跑通回归

### User Story 4 - 规则清单能回答"为什么被拒" (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 一次被拒绝的操作，**When** 查阅返回的规则号，**Then** 能找到该规则的完整说明与修复建议
2. **Given** 一条规则已被废止，**When** 查阅，**Then** 保留废止记录与替代规则，不直接删除

## Requirements

### Functional Requirements

- **FR-001**: 契约 YAML 无法表达的规则 MUST 被显式固化为带编号的规则条目
- **FR-002**: 每条规则 MUST 包含编号、含义、判定式、实现位置与至少一个反例
- **FR-003**: 引擎 MUST 在写入路径上执行全部可自动判定的规则，违反返回 4xx 且不落库
- **FR-004**: 技能 MUST 使用与引擎同源的规则定义，不得各自实现一份
- **FR-005**: 同一输入在引擎与技能两侧的判定结果 MUST 一致
- **FR-006**: 新增或修改规则 MUST 同步更新规则文档，并附带覆盖正例与反例的测试
- **FR-007**: 规则清单 MUST 可枚举，支持按表、按阶段、按规则号检索
- **FR-008**: 被拒绝的操作 MUST 返回规则号与修复建议
- **FR-009**: 废止规则 MUST 保留废止记录与替代关系，不得静默删除
- **FR-010**: 规则校验 MUST NOT 让合法写入产生可观测的性能退化（单次写入附加上限 50 ms）

### Edge Cases

- 规则之间存在优先级冲突时，须在清单中写明顺序，不得由实现自行决定
- 批量写入时逐条校验与整体原子性如何兼顾：任一条违反则整批失败，不得部分成功
- 历史数据已违反新规则时，引擎默认拒绝新写入但不回改历史；历史清理由专门动作执行
- 规则涉及跨项目数据时，校验范围以目标项目为界
- 引擎不可用或校验超时时，写入应按失败处理，不得降级为放行

## Success Criteria

- **SC-001**: 契约外规则 100% 进入规则清单，无一条只存在于口头或注释中
- **SC-002**: 绕过技能直接调用接口的违规写入 100% 被引擎拒绝
- **SC-003**: 引擎与技能对同一组规则用例的判定结果完全一致
- **SC-004**: 新增规则时未补文档或未补测试的提交比例降为 0

## Key Entities

- **规则条目**：一条契约外规则，含编号、含义、判定式、实现位置、反例与状态
- **规则清单**：全部规则条目的集合，可按维度检索
- **同源定义**：引擎与技能共用的规则来源，避免两套实现
- **反例测试**：为每条规则构造的应被拒绝的输入
