# Feature Specification: 交付范围与测试范围解耦

**Feature Branch**: `035-scope-decouple`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 035-AR

## 背景与问题证据

| 项 | 证据 | 影响 |
|---|---|---|
| 用例来源被强制挂本版 | `tf_test_plan.py:90`：`attached = spec_id in version_specs`，不满足直接 `SkillFailure` | 想复测历史能力，必须先把该需求重新挂到本版 |
| 由此产生重复挂载 | 026–028 同时挂在 v0.7.1 / v0.7.3 / v0.7.4，029–031 同时挂在 v0.7.2 / v0.7.3 / v0.7.4，另有 007-AR 在 v0.5.0 / v0.5.1 | 7 条需求 13 处重复；同一交付工作被重复计入 |
| 两个范围混成一个字段 | 版本的「独立需求管理」既被当作交付记录，又被当作测试范围 | 交付统计失真，且违反 033 的唯一性规则 |

本需求把两个范围分开：**交付范围**回答"这一版新增、修改、补齐了哪些工作"；**测试范围**回答"这一版需要验证哪些能力，包括历史能力"。两者通过用例表间接连接，不共用同一个字段。

## Clarifications

### Session 2026-11-23

- Q: 版本内的用例能否来自没挂在本版的需求？ → A: 能。用例是资产，验证的是能力；能力属于哪个需求与它是否属于本版交付无关。
- Q: 那版本的交付范围怎么算？ → A: 只看「独立需求管理」与「依赖需求管理」，由 033 的唯一性规则约束。
- Q: 纯回归版本（只重跑历史用例、无新交付）允许吗？ → A: 允许，此时交付范围为空，用例范围非空。

## User Scenarios & Testing

### User Story 1 - 复测历史能力而不重复挂载需求 (Priority: P1)

测试人员要为 v0.7.3 复测 026–031 的能力，但这些能力早在本版之前的版本交付完成了。

**Why this priority**: 这是当前 13 处重复挂载的直接成因。

**Independent Test**: 在交付范围为空或只含新需求的版本里，把 026-AR 的用例纳入本版并执行，全程不修改「独立需求管理」。

**Acceptance Scenarios**:

1. **Given** v0.8.0 的交付范围只有 033-AR，**When** 把 026-AR 的用例纳入本版，**Then** 用例进入本版 run 集合，`独立需求管理` 保持不变
2. **Given** 026-AR 已在 v0.7.1 交付完成，**When** 本版纳入它的用例，**Then** 026-AR 不被再次计入本版交付，`独立需求已完成/总数` 不因它变化
3. **Given** 用例来自版本外的需求，**When** 查询该用例的归属，**Then** 仍能沿 `case → indep` 追溯到 026-AR

### User Story 2 - 交付范围只记录本版工作 (Priority: P1)

**Why this priority**: 交付范围的准确性直接决定版本统计与发布说明。

**Independent Test**: 对任一已发布版本，其「独立需求管理」并集不与其他版本重叠（033 的 C1）。

**Acceptance Scenarios**:

1. **Given** 一个版本只修改了既有能力，**When** 记录交付范围，**Then** 只出现依赖需求，不出现被修改能力的独立需求
2. **Given** 一个版本只做回归，**When** 记录交付范围，**Then** 两个关联均为空，`独立需求是否完成` 与 `依赖需求是否完成` 按空集为真处理
3. **Given** 版本交付范围为空但用例范围非空，**When** 计算发布闸门，**Then** 六节点仍按各自判据推进，不因空集被跳过

### User Story 3 - 用例纳入时的校验仍有约束 (Priority: P2)

放宽来源不等于放任，纳入本版的用例仍需满足基本条件。

**Acceptance Scenarios**:

1. **Given** 一条用例所属的独立需求尚未验收通过，**When** 把该用例纳入本版，**Then** 允许纳入，但在报告中标注"能力未验收"
2. **Given** 一条用例的场景在源规格中已消失，**When** 纳入本版，**Then** 拒绝并提示源场景缺失
3. **Given** 同一条用例已被纳入另一个版本，**When** 纳入本版，**Then** 允许（用例可跨版本重复验证），并生成新的 run 行而不是覆盖

### User Story 4 - 拒绝把已交付需求重复挂载 (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 026-AR 已挂在 v0.7.1，**When** 通过登记流程把它挂到 v0.8.0，**Then** 拒绝并提示改为纳入用例
2. **Given** 一次拒绝发生，**When** 回读目标版本，**Then** 交付范围保持操作前状态

## Requirements

### Functional Requirements

- **FR-001**: 版本内的用例 MUST 允许来自未挂在本版本的独立需求
- **FR-002**: 版本 MUST 只把本版新增、修改、补齐的工作计入「独立需求管理」与「依赖需求管理」
- **FR-003**: 已完成交付的独立需求 MUST NOT 在新版本重复挂载（与 033 的 C1 一致）
- **FR-004**: 系统 MUST 允许交付范围为空的版本（纯回归版本），并保持六节点判据可执行
- **FR-005**: 用例 MUST 保留到其来源独立需求的可追溯关联（`case → indep`），不因是否挂本版而丢失
- **FR-006**: 纳入本版时 MUST 校验来源场景在源规格中仍然存在，缺失则拒绝
- **FR-007**: 同一用例进入不同版本时 MUST 生成各自独立的执行行，不得互相覆盖
- **FR-008**: 用例所属需求尚未验收时 MUST 允许纳入，并在报告中标注该状态
- **FR-009**: `tf-test-plan` MUST 移除"用例来源规格必须挂在当前版本"的强制约束
- **FR-010**: 交付范围与用例范围 MUST 在版本表上分字段表达，不得共用同一关联字段

### Edge Cases

- 源规格的场景编号被重命名后，已纳入本版的用例如何处理：按场景号找不到时必须报错，不得静默跳过
- 一条用例的来源需求被放弃（dropped）后，该用例仍可被纳入其他版本做回归，但报告中需标注来源能力已放弃
- 纯回归版本连续出现时，各版本的用例执行行相互独立，不得复用上一版结果
- 版本交付范围为空且用例范围也为空时，"用例是否完成"按空集为真，但该版本不应被误判为有测试活动
- 用例来源需求跨多个项目时，关联字段的取值以用例表所属项目为准

## Success Criteria

- **SC-001**: 复测历史能力不再需要把独立需求重新挂版，重复挂载从 13 处降为 0
- **SC-002**: 任一版本的交付范围只包含本版工作，版本间并集无交集
- **SC-003**: 任一条用例可在一次查询内追溯到来源需求，且不依赖它是否挂在本版
- **SC-004**: 纯回归版本可正常推进六节点并满足发布闸门

## Key Entities

- **交付范围**：版本记录的本版新增/修改/补齐工作，由独立需求与依赖需求两个关联表达
- **测试范围**：版本记录的本次需要验证的能力集合，由用例关联表达，可与交付范围无关
- **用例**：能力的验证资产，归属某个独立需求，可被任意版本多次纳入执行
- **执行行**：某条用例在某个版本的一次执行，行 id 由 `<版本号>--<用例号>` 构成
