# Feature Specification: 阶段产物与证据强制

**Feature Branch**: `038-stage-evidence`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 需求 038-AR

## 背景与问题证据

| 项 | 证据 | 影响 |
|---|---|---|
| 阶段状态大面积空缺 | 线上 31 条独立需求 × 8 个阶段字段 = 248 个状态，其中 90 个为空，占 36.3% | 状态无法作为判据，也无法说明这些阶段是否发生过 |
| 八个阶段只有一处写入者 | 全仓库只有 `tf-dev-implement` 与 `tf-dev-check` 写 `speckit-implement状态`；constitution / specify / plan / task / clarify / analyze / checklist 七个字段没有任何技能写入 | 不是漏填，是写入通道不存在，只能手工填 |
| 有勾选的任务但无计划 | 026–031 六个目录均有 `spec.md` 与已勾选的 `tasks.md`，`plan.md` 全部缺失 | 任务从何而来无法回答，过程不可审计 |
| 完成判定只看勾选 | `tf-dev-implement` 只校验 `tasks.md` 已全部勾选 | 勾选是文档里的记录，不等于实现存在、也不等于验证通过 |

**空值首先证明流程执行与状态记录没有受到约束**，不能据此推导出粒度问题。本需求把"阶段状态"从一个可以随便填的枚举，变成必须有产物支撑的断言。

## Clarifications

### Session 2026-11-23

- Q: 历史那 90 个空值要不要补填？ → A: 不补。未记录保持"无法证明"，批量补成 done 等于伪造证据。
- Q: 复用已有的宪法和设计算不算缺产物？ → A: 不算，但必须记录复用了哪一份、哪个版本，以及复用后是否重新确认仍适用。
- Q: 一份规格做完，版本就算完成了吗？ → A: 不算。版本完成由六节点判定，单规格完成只是一个输入。

## User Scenarios & Testing

### User Story 1 - 阶段状态必须能被证明 (Priority: P1)

看板上一个阶段显示 done，就应该能指向支撑它的产物和验证结果。

**Why this priority**: 状态不可证明，则所有以状态为输入的判定都失去意义。

**Independent Test**: 对任一显示 done 的阶段，能取出其产物路径与验证证据；取不出的判为无效状态。

**Acceptance Scenarios**:

1. **Given** 某规格的 `speckit-plan状态` 为 done，**When** 查询其证据，**Then** 返回 `plan.md` 路径与最近一次一致性检查结果
2. **Given** 某规格 `tasks.md` 已全部勾选但 `plan.md` 不存在，**When** 校验，**Then** `speckit-plan状态` 不得为 done，`speckit-implement状态` 也不得据此置 done
3. **Given** 某阶段没有任何产物，**When** 尝试置 done，**Then** 拒绝并返回该阶段要求的产物清单

### User Story 2 - 复用既有产物需留痕 (Priority: P1)

宪法、设计基线这类内容不必每次重写，但复用要能被看到。

**Why this priority**: 不记录复用，"没写"与"复用了"无法区分，等于给伪造留口子。

**Independent Test**: 对一次复用，能查出复用的来源版本与复用时的确认结论。

**Acceptance Scenarios**:

1. **Given** 本次规格复用项目宪法且未修改，**When** 记录 constitution 阶段，**Then** 写入宪法版本号与"未修改"标记
2. **Given** 本次变更复用上一版的设计文档，**When** 记录，**Then** 写明来源版本与"复用后重新确认仍适用"的结论
3. **Given** 复用的来源版本已被新版本取代，**When** 校验，**Then** 提示基线已过期，要求重新确认

### User Story 3 - 历史空值保持"无法证明" (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 历史记录中某阶段为空，**When** 生成报告，**Then** 显示"无法证明"而不是"未完成"或"已完成"
2. **Given** 有人尝试批量把历史空值补成 done，**When** 提交，**Then** 拒绝提交，历史空值不得批量补写
3. **Given** 需要对历史规格补做阶段，**When** 执行，**Then** 允许补做并记录补做时间与操作者，不得伪装成当时完成

### User Story 4 - 单规格完成不等于版本完成 (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 本版全部规格都已 accepted，**When** 查询版本状态，**Then** 六节点仍按各自判据独立推进，不因规格齐备自动置 done
2. **Given** 版本内只有部分规格完成，**When** 推进开发节点，**Then** 拒绝并列出未完成的规格

## Requirements

### Functional Requirements

- **FR-001**: 每个阶段 MUST 定义其产物与验证方式，并在置 done 时校验产物存在
- **FR-002**: 任一阶段置 done MUST 附带可定位的证据引用，无证据不得置 done
- **FR-003**: 八个阶段字段 MUST 各自有明确的写入者（技能或人），不允许存在无写入者的字段
- **FR-004**: 复用既有产物 MUST 记录来源与版本，以及复用后的适用性确认
- **FR-005**: 复用产物的来源版本已过期时，系统 MUST 提示并要求重新确认
- **FR-006**: 历史空值 MUST 呈现为"无法证明"，不得自动推断为完成或未完成
- **FR-007**: 系统 MUST 拒绝把历史空值批量补写为 done
- **FR-008**: 补做历史阶段 MUST 记录补做时间与操作者，与当时完成区分
- **FR-009**: 单份规格完成 MUST NOT 直接导致版本节点置 done
- **FR-010**: 校验 MUST 区分"产物存在"与"产物通过验证"，后者才可作为置 done 的依据

### Edge Cases

- 某阶段的产物被后续变更覆盖时，历史 done 是否仍成立：以记录的产物快照或版本号为准，无快照则标注为"证据不可回溯"
- 一个阶段同时由技能和人写入时，以最后一次带证据的写入为准，且保留两次记录
- 产物存在但内容与当前规格不一致时，校验应报不一致而不是静默通过
- 规格被放弃（dropped）后，其未完成阶段应停止校验，不得继续要求补齐

## Success Criteria

- **SC-001**: 八个阶段字段全部有写入者，不再存在只能手工填写的字段
- **SC-002**: 任一显示 done 的阶段都能取出产物与验证证据，无法取出的为 0 条
- **SC-003**: 历史 90 个空值在报告中一律显示为"无法证明"，无一条被自动改写
- **SC-004**: 026–031 这类"有 tasks 无 plan"的规格在校验中被正确拦下

## Key Entities

- **阶段**：规格生命周期中的一个步骤，有名称、产物、验证方式与状态
- **产物**：阶段产生的文件或记录，如 `spec.md`、`plan.md`、`tasks.md`、验证报告
- **证据引用**：指向产物的可定位引用，用于证明状态成立
- **复用记录**：描述本次复用哪份既有产物、哪个版本、复用后的确认结论
- **补做记录**：标记某阶段是在事后补做，含补做时间与操作者
